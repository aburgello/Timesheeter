Engineering audit

Technical audit — the core of the Timesheeter app

A code-level review of the six subsystems that carry the day-to-day work: job identity and resolution, territory (country) resolution, the timesheet entry pipeline, the Wrike sync and cache, the Management surface, and the auth / data layer. Every finding cites the file and line it was read from.

1How the audit was run

Six audit agents worked in parallel, one per subsystem. Each read the actual source (not a summary of it) and returned findings that had to be grounded in a file:line reference with a concrete failure scenario. The seven findings rated critical or high were then re-read by a second, adversarial pass — an independent agent re-walked the cited code path for each one and had to confirm, refute, or mark it plausible. All seven were confirmed. That second pass is the difference between a list of suspicions and a list of things that actually fail.

SeverityCountMeaning
Critical1Security / wholesale data risk — anyone with the app can reach the data layer.
High6Wrong result or lost work under common conditions.
Medium18Wrong result on an edge case, or a fragile path that is easy to trip.
Low16Inconsistency, observability, or a latent risk that does not bite today.
Scope. This is a static, code-read audit. It did not run the app, touch the database, or call the live Wrike or Supabase APIs — so a finding confirmed here is confirmed in the code, not in live data. Where a scenario depends on data (e.g. “a user has 1,200 rows”), the code path that causes the failure is verified; the trigger is the realistic part.

2The seven that matter

Everything below is a real, walkable failure in the code. Start here.

CriticalRLS write policies are wide open; the admin gate is UI-only
supabase/schema.sql:509

Summary. jobs, positions, job_categories, job_departments, project_descriptions, job_sync_kept, board_now, wrike_tasks_cache, wrike_sync_meta and the campaign/canvas/dooh tables all carry for all to authenticated using (true) with check (true) — and every visitor becomes an authenticated user via signInAnonymously() (src/lib/supabaseClient.js:21) against the anon key embedded at supabaseClient.js:5.

Failure. Anyone who opens the app, signs in anonymously, and knows the anon key can PATCH/DELETE on /rest/v1/jobs, set positions.hourly_rate = 0, or wipe board_now directly. MANAGEMENT_IDS gates the React page (Management.jsx:6041, App.jsx:460), never the database. The only policy that enforces the admin allowlist (KUAWDLVN, KUAQT4JC) is profiles_write (schema.sql:516).

HighScan keeps only the first folder per XY code — an archived copy can shadow the live one
src/lib/wrikeCampaign.js:345

Summary. scanStudioJobNumbers de-dups by code with a first-writer-wins seen set before computing ancestry, so the folder the scan describes is whichever one Wrike happens to list first.

Failure. Code XY025716 on both a live folder (SONY › Focker In-Law) and an _Archive copy. If the archive copy is enumerated first, seen.has(code) skips the live folder entirely; the job is reported archived, gets film “Archive”, and vanishes from the default “Active only” view — even though the multi-parent machinery is supposed to keep live copies alive. It only walks one folder’s own parents; it cannot compare two folders that carry the same code.

HighThe scan re-creates the mangled job numbers it was meant to fix
src/lib/wrikeCampaign.js:359

Summary. Any folder title containing " : " is copied verbatim into job_number — so a title whose code position carries a suffix, like The Odyssey : XY025716_INTL_DIGITAL_OUTDOOR_CAMPAIGN_MARKETS, INT - DOOH…, is re-registered as-is. That is the exact “self-perpetuating” shape wrikeHelpers.js:16-20 says must never enter the code position.

Failure. The 23 legacy rows documented at wrikeHelpers.js:17-18 came from folders still named this way. On the next scan the mangle sits back in the code position; pull-time resolveJobNumber and getJob adopt it verbatim. The fix that hardened the pull path was never applied to the scan path.

HighLogged rows are stamped with the logging date, not the selected day
src/hooks/useTaskActions.js:90

Summary. handleLogTask writes dayOfWeek: selectedDay but date: new Date().toLocaleDateString('en-GB') — always today. useTasks.toDb derives work_date from date (useTasks.js:38), and the week view keeps only rows where workDate >= weekStart (useTasks.js:147-150).

Failure. On Sunday 2026-08-09, selecting Monday and logging 1h writes dayOfWeek=Monday, date=09/08/2026, work_date=2026-08-09. When Monday arrives, weekStart moves to 2026-08-10, the filter excludes the row, and the Monday entry vanishes from the grid while staying in the DB. Within a week, backfilling Monday on a Wednesday stores Wednesday’s date on a Monday row. The Legacy modal has the same mismatch (LegacyTimesheets.js:281-323 vs useLegacyRows.js:65).

HighA purge with a stale dictionary permanently deletes still-relevant tasks
src/hooks/useWrikeCache.js:651

Summary. sync() purges any task that fails filterToMotionTeam, but that filter matches assignees and DIGITAL folders against a contact_dictionary that is only refreshed every 24h (useWrikeCache.js:604) and is never checked for freshness.

Failure. Wrike adds a new Motion member Pat; a task is reassigned to Pat. With a 20h-old contact dict, motionTeamShortName(contactDictionary[patId]) is undefined, the task fails the filter, lands in droppedIds, and is DELETEd from the shared wrike_tasks_cache for the whole team. Its updatedDate is now older than the advanced last_synced_at, so no later delta sync re-fetches it. The task stays gone until someone presses the manual sync button.

HighStudioAnalytics drops every CSV-imported row from the hours charts
src/components/StudioAnalytics.jsx:47

Summary. parseDdMmYyyy splits on /, so an ISO date (2026-01-05) parses to null. The CSV importer writes exactly that shape (worker/index.js:187-198, documented in migration 20260810090000), while everything written in the app is 09/08/2026.

Failure. The “Hours logged” KPI (hours30) and “Hours logged per week” silently drop every imported row, while “Hours by client” and “Hours by department” do no date parse and include them — so the four charts disagree and the headline number undercounts imported time. The authoritative work_date column is selected by the feed yet ignored.

HighTimelog dedup reads at most 1000 rows
src/lib/supabaseClient.js:87

Summary. fetchExistingTimelogIds does a plain .select() with no .range() pagination — the exact failure mode selectAll was written to fix (its own comment, lines 42-47). PostgREST caps at 1000 rows with no error.

Failure. A user with 1,200 timelogged task rows gets 200 ids missing from the dedup set. A later pull of one of those timelogs (useTaskActions.js:192/216, LegacyTimesheets.js:1413) re-inserts a duplicate row carrying the same wrike_timelog_id.

3Job identity & resolution

jobKey (wrikeHelpers.js:56-60) reduces any label — bare code, suffixed folder title, or canonical Film : XY025716, Desc — to its first XY\d{5,6} match. useJobLookup keys the whole book by that key, keeps the richest row on a tie, and ensureJob only ever gap-fills blank fields. The scan walks the folder tree, derives film/client/region by climbing ancestry, and a unique expression index (substring(job_number from 'XY\d{5,6}'), schema.sql:434) enforces one row per code. This slice carries two of the seven confirmed highs (the shadowing archive copy and the re-mangled canonical branch) plus the medium risks below.

4Territory (country) resolution

The resolver reads a country only where someone deliberately put one, in order: last tokens of the task name → parent task name → folder climb → Country custom field matched by id (countryCodes.js, countryField.js). Alias precedence is territory names < REGION_ALIASES < MAGI_MARKET_CODES < agreed exceptions. The design rule (“read, never guessed”) holds up well; the findings here are the places the rule is bent by accident.

5Timesheet entry pipeline (Tracker + Legacy)

All rows for both surfaces go through useTasks — the single store. The DB keeps time as H:MM text while memory keeps exact seconds; toDb/fromDb and updateTask convert via the shared parseTimeToSeconds/secondsToHM. Dates live in date (text) plus a derived work_date used for the week filter. The confirmed high (logging-date vs selected-day) sits at the top of this stack; the rest are rounding and representation mismatches.

6Wrike sync & cache

A team-shared mirror of Wrike tasks: hydrate from IndexedDB, delta-pull rows past a local cursor with 24h overlap, enrich, upsert, mirror, purge what dropped out of relevance, and stream live updates through a Supabase Realtime subscription. The confirmed high (stale-dictionary purge) is the expensive one here — it is the one path that deletes shared data on a false negative. The rest are windowing and error-handling gaps.

7Management surface (Job Book, scans, analytics)

The Management surface exports JobsSetupSection/JobBookSection/JobsFeedSection (the standalone Job Book is a three-tab shell over them). The Studio Job Scan reconciles book rows against the folder scan, classifies each code as correction/fixable/kept/redundant, inserts new codes in 200-row chunks, and rewrites or deletes on confirm. StudioAnalytics reads the studio timesheet through the worker feed but reads the Wrike-side tiles from the motion-filtered shared cache. One confirmed high (CSV dates) plus the reconciliation gaps below.

8Auth, access & data layer

The client boots an anonymous Supabase session and stamps the Wrike user ID into JWT user_metadata; RLS reads that. Per-user rows (tasks) are scoped by wrike_user_isolation; profiles by profiles_read/profiles_write. This slice holds the audit’s only critical: the anonymous-everyone-is-authenticated model plus wide-open write policies means the admin allowlist is enforced in the UI only.

9Reading the severity

Nothing here requires “this won’t happen”. The two that look worst are the RLS posture (critical) and the logging-date stamp (high) — the second is something a real user hit the week this audit ran (Sunday → Monday). The purge and the scan-shadow findings both silently destroy or hide data and have no automatic recovery. The cheapest wins are the date-stamp fix, the job_sync_kept ordering fix, and switching fetchExistingTimelogIds to the existing selectAll.
